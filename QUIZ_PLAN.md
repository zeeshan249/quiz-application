# Plan: Realtime Synchronized Quiz System

## Decisions locked in
- **Pacing:** Synchronized (lockstep) — the **same question is shown to everyone at once**. Server-driven
  timeline: **20s to answer → 6s reveal break** (a bar showing the % correct vs % wrong) → next question,
  auto-advancing until the quiz ends. `answer_seconds` (20) and `reveal_seconds` (6) are configurable per session.
- **Scope:** Full end-to-end (foundation → admin → gameplay → scoring → leaderboard).
- **Participant UI:** Bootstrap 5 (reuses the login-page setup; public + mobile-friendly).
- **Identity:** **Name (required)** + shared 6-digit code. **No phone, no OTP, no PII beyond the typed name.**
  The name is the leaderboard label. An anonymous **session/device token** is generated on join for dedupe.
- **Code:** 6 digits, per-quiz, set/generated by admin. Unique among **active** sessions (`lobby`/`live`); reusable once `ended`.

## Join → lobby → start flow
1. The 6-digit code is given to everyone (projected/announced by the admin).
2. User opens the join page → enters **name + code** → joins.
3. User lands in a **lobby** and waits; the live counter ticks up as others join.
4. **Admin clicks Start** → every lobby screen flips into the quiz at once (`QuizStatusChanged → live`).
5. From there the server drives a **synchronized timeline**: everyone sees the same question, gets **20s** to
   answer, then a **6s reveal** (correct-vs-wrong bar), then the next question — in lockstep for all.

## Device token (dedupe) — important note
Browsers do **not** expose a real hardware device ID (privacy). So "device id" here = an anonymous **token**
we generate on first join and store in the Laravel **session cookie** (optionally mirrored to `localStorage`
for resilience). It stops **casual** double-counting (refresh, reopen, back button) — the same browser maps to
the same participant. It does **not** stop incognito / another browser / another phone; that would need
verifiable identity (account/OTP), which is explicitly out of scope. Best-effort dedupe is fine for a live quiz.

## Codebase starting point
- Fresh **Laravel 13 + Livewire 4** app. No broadcasting / Reverb / Echo installed yet.
- Queue defaults to `database`. Bootstrap login already set up with split Vite entries.
- Existing admin area uses Gentelella theme behind admin auth (`user_type`).

## Synchronized implication
Questions **are** pushed to everyone at once. The server owns the clock and broadcasts each question with an
authoritative deadline; every client counts down to the **same** `ends_at`, so screens stay in lockstep
without trusting client time. Realtime carries: the join counter, the lobby → live flip, **each question
(text + options + deadline)**, the **reveal stats** (correct/wrong %), and the live leaderboard.

**Timeline authority:** the server broadcasts `QuestionStarted { question, options, ends_at (+20s) }`. At the
deadline clients lock input and auto-submit blanks; the server tallies and broadcasts
`QuestionRevealed { counts, correct_pct, wrong_pct, reveal_ends_at (+6s) }`; at that deadline it broadcasts the
next `QuestionStarted`, or `QuizStatusChanged → ended` after the last one. The transition driver is a
**server-side sequence** (scheduled command / dispatched job chain with `20s`+`6s` delays) so the timeline
runs even if no host browser is open.

**Answer secrecy trade-off:** because options are broadcast to everyone, `is_correct` is **never** sent to
clients during the answer window — the correct option is only revealed in the `QuestionRevealed` aggregate
(percentages). Scoring is computed server-side on submit.

## 2. Data model (migrations + Eloquent models)
- **`question_sets`** — `title`, `created_by`, `created_at`, `updated_at`. Reusable templates of questions; 
  one set can be used in multiple quiz sessions.
- **`quiz_sessions`** — `title`, `question_set_id` (FK → `question_sets`), `join_code` (6-digit string), 
  `status` enum(`lobby`/`live`/`ended`), `created_by`, `started_at`, `ended_at`, `answer_seconds` (default 20), 
  `reveal_seconds` (default 6), plus **synchronized-timeline state**: `current_question_id` (nullable — added 
  after `questions` exists to avoid a circular FK), `phase` enum(`question`/`reveal`, nullable), `phase_ends_at` 
  (authoritative deadline broadcast to clients). Uniqueness of `join_code` among active sessions enforced in 
  validation (ended codes reusable).
- **`questions`** — `question_set_id`, `text`, `position`, `points`, optional `time_limit`
  (per-question override; defaults to the session `answer_seconds`).
- **`question_options`** — `question_id`, `text`, `is_correct` (idiomatic over a JSON column).
- **`participants`** — `quiz_session_id`, `name` (required, leaderboard label), `token` (anonymous dedupe id),
  `score`, `joined_at`, `finished_at`. **No phone / PII.** **Unique(`quiz_session_id`, `token`)** = one entry
  per browser per quiz; this table **is** the counter source.
- **`answers`** — `participant_id`, `question_id`, `question_option_id?` (null = timed out), `is_correct`,
  `response_ms`, `points_awarded`. **Unique(`participant_id`, `question_id`)** = one answer per question.
  Indexed **`(question_id, is_correct)`** so the **reveal bar** (count correct vs wrong per question) is a fast
  grouped query — this table is the source for the correct/wrong percentages shown in the 6s break.
- Models with relationships + a `QuizSession::generateUniqueCode()` helper.

## 3. Broadcast events (public channel `quiz.{id}`)
Public channel — participants aren't Laravel-authed, and only non-sensitive aggregate data is broadcast
(never `is_correct` per option during the answer window).
- **`ParticipantJoined`** → `{ total }` — fires the increment counter.
- **`QuizStatusChanged`** → `{ status }` — flips lobby screens into the quiz on Start, to results on End.
- **`QuestionStarted`** → `{ question, options[], ends_at }` — pushes the same question to everyone and starts
  the synchronized **20s** countdown.
- **`QuestionRevealed`** → `{ counts:{correct,wrong,total}, correct_pct, wrong_pct, reveal_ends_at }` — ends the
  answer window and drives the **6s correct-vs-wrong bar**.
- **`LeaderboardUpdated`** → top N — fires on reveal.

## 4. Participant flow (Bootstrap, public routes)
Dedicated public `layouts/quiz` layout (loads the Bootstrap `quiz.js` entry). Livewire components:
- **`JoinQuiz`** (`/join`) — **name + code** form. Validates: active `lobby` session with that code. Generates
  an anonymous token (session cookie, optionally mirrored to `localStorage`); if that token already has a
  participant in this session, reuses it (no double-count). Creates `Participant` (name + token), stores
  `participant_id` in session (survives refresh), fires `ParticipantJoined`.
- **`QuizLobby`** — waiting screen with the **animated live counter** (Alpine tween + Echo listener);
  auto-advances when `QuizStatusChanged → live`.
- **`QuizPlay`** — synchronized engine driven by Echo: on `QuestionStarted` it renders the shared question and
  runs an **Alpine countdown to `ends_at` (20s)**; on timeout or submit it locks input and posts the answer
  (server scores: **flat — 1 point if correct, 0 if wrong**; `response_ms` kept only as a leaderboard
  tiebreaker, re-validated). On `QuestionRevealed` it swaps to the
  **6s correct-vs-wrong bar** (animated %), then waits for the next `QuestionStarted`. Late/duplicate submits
  are rejected server-side (deadline + unique constraint).
- **`QuizResults`** — final score + live leaderboard.

## 5. Admin flow (Gentelella, behind existing admin auth)
- **`QuestionSetIndex`** (`/admin/question-sets`) — list/create question sets; manage questions/options per set.
- **`QuizIndex`** (`/admin/quizzes`) — list/create sessions, each bound to an existing question set; auto-generate 
  or set the 6-digit code.
- **`QuizControl`** (host screen) — big join code to project, **live join counter**, **Start**/**End**
  buttons, the current question with its **live answer tally + correct/wrong bar** on reveal, and a live
  leaderboard. Start kicks off the **server-driven question sequence** (20s answer → 6s reveal → next).

## 6. The increment counter
Alpine component holding `count`; an Echo listener on `quiz.{id}` updates it on `ParticipantJoined`; a
`requestAnimationFrame` tween animates old → new value. DB-backed total = monotonic, refresh-proof.

  scheduling.
- Separate `quiz.js` Vite entry (isolates Bootstrap from Gentelella).
- Name-only identity + anonymous session/device token (no phone, no OTP, refresh-safe, best-effort dedupe).

● Right — I never actually wrote the scoring logic; I just set up the columns for it. Let me explain what I intended and  how the pieces connect, because the points live in two places for a reason.


  The two columns

  - questions.points = the maximum this question is worth (I defaulted it to 1000). It's the ceiling, not what anyone necessarily gets.
  - answers.points_awarded = what this participant actually earned for this question, computed at submit time.
  - answers.response_ms = how long they took to answer (milliseconds from when the question started to when they submitted). This is the input that makes fast answers worth more.

  So questions.points is the knob; response_ms is the speed; points_awarded is the result.

  The Kahoot-style formula

  Wrong answer → 0. Correct answer → somewhere between half and full points, scaled by how fast they were:

  $max      = $question->points;              // e.g. 1000
  $limitMs  = ($question->time_limit ?? $session->answer_seconds) * 1000; // e.g. 20000

  if (! $isCorrect) {
      $awarded = 0;
  } else {
      $fraction = 1 - ($responseMs / $limitMs) / 2;   // 1.0 (instant) → 0.5 (last moment)
      $awarded  = (int) round($max * $fraction);
  }

  Walk through it with points = 1000, limit = 20s:

  ┌───────────────────┬─────────────┬──────────┬────────────────┐
  │    Answered at    │ response_ms │ Fraction │ points_awarded │
  ├───────────────────┼─────────────┼──────────┼────────────────┤
  │ instantly         │ 0           │ 1.00     │ 1000           │
  ├───────────────────┼─────────────┼──────────┼────────────────┤
  │ 5s                │ 5000        │ 0.875    │ 875            │
  ├───────────────────┼─────────────┼──────────┼────────────────┤
  │ 10s (halfway)     │ 10000       │ 0.75     │ 750            │
  ├───────────────────┼─────────────┼──────────┼────────────────┤
  │ 20s (buzzer)      │ 20000       │ 0.50     │ 500            │
  ├───────────────────┼─────────────┼──────────┼────────────────┤
  │ wrong / timed out │ —           │ —        │ 0              │
  └───────────────────┴─────────────┴──────────┴────────────────┘

  The /2 is what keeps a correct-but-slow answer worth at least half — so being right always beats being fast-and-wrong. That's the standard Kahoot feel. If you'd rather it decay all the way to 0, drop the /2: 1 - $responseMs / $limitMs.

  Then the participant's total

  participants.score is just the running sum of their points_awarded, bumped on each submit:

  $participant->increment('score', $awarded);

  …and that score column is what the leaderboard sorts by.

  If you don't want speed to matter

  Then the whole response_ms / fraction machinery is unnecessary — set points_awarded = $isCorrect ? $question->points : 0 and make questions.points default 1 (flat "1 point per correct answer"). In that case response_ms is still worth
  keeping as a tiebreaker (whoever reached the same score faster ranks higher), but it wouldn't affect the points themselves.

  Do you want speed-weighted scoring or flat scoring? That decides whether questions.points should default to 1000 or 1 — say the word and I'll adjust the migration.

> what is this in    $table->enum('phase', ['question', 'reveal'])->nullable(); quiz_sessions table                                                                                                                                          
● That column tracks which part of the synchronized timeline the quiz is currently in, right now, for the live session. It's the server's "what should everyone's screen be showing" flag.

  Remember your loop for each question: 20s answer → 6s reveal bar → next question. Those are two distinct phases:

  - phase = 'question' — a question is on screen, the 20s answer window is running. Players can submit.
  - phase = 'reveal' — the 6s break, showing the correct-vs-wrong bar. Input locked, no submissions accepted.
  - phase = null — not in a question cycle at all (quiz is draft, lobby, or ended).

  It works together with the other two sync columns:

  ┌─────────────────────┬──────────────────────────────────────────────────────────┐
  │       Column        │                          Holds                           │
  ├─────────────────────┼──────────────────────────────────────────────────────────┤
  │ current_question_id │ which question is active right now                       │
  ├─────────────────────┼──────────────────────────────────────────────────────────┤
  │ phase               │ what stage of that question (answering vs revealing)     │
  ├─────────────────────┼──────────────────────────────────────────────────────────┤
  │ phase_ends_at       │ when this stage ends (the deadline broadcast to clients) │
  └─────────────────────┴──────────────────────────────────────────────────────────┘

  Read together they fully describe the live state: "Question #5, in the question phase, ending at 14:32:20." Your server-side timeline driver flips these on each transition — set phase='question' + phase_ends_at = now+20s, wait, set
  phase='reveal' + now+6s, wait, advance current_question_id and repeat.

  Why store it in the DB instead of just broadcasting it: if a player refreshes mid-quiz, the server reads these three columns to rebuild exactly what they should see and how many seconds are left — without them, a refresh would lose the
  player's place. It's also what makes the server (not the client's clock) the source of truth for the timer.
